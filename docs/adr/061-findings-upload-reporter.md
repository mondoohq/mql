# ADR 061: A reporter on findings uploads

## Status

Proposed

## Context

The public Finding Exchange contract is `providers-sdk/v1/upstream/fex/fex.proto`.
`FindingsUploadRequest` carries the findings, a `source`, `import_started_at` for a
full pull, `complete_kinds` (field 9) and `scanned_components` (field 13). With a
full pull the platform closes, by absence, every finding of that source and kind on
the assets the upload covers.

One producer can send two kinds of results under one source. A code scanner sends
code-quality and security findings and, in a separate mode, findings about sensitive
data flows. Both are `FINDING_KIND_FINDING` documents of the same source, so
`complete_kinds` cannot tell them apart. Nothing in the request tells the platform
which of the two modes a full pull was complete for, so a full pull of one mode closes
the other mode's findings.

Fields 7, 8 and 10 to 12 of `FindingsUploadRequest` are used by the platform's copy of
the message and are not assigned in mql. Field 14 is free in both.

## Decision

1. **`string reporter = 14` on `FindingsUploadRequest`.** Optional. It names the
   producer mode the upload speaks for, as `<producer>:<mode>`, for example
   `<tool>:code` and `<tool>:dspm`. With `import_started_at` set, the platform closes
   by absence only the findings last reported under the same reporter. Empty keeps
   today's behaviour. `complete_kinds` still narrows by kind; both apply. An upload
   without `import_started_at` closes nothing, whatever the reporter.
2. **The value is not free text.** Format `^[a-z0-9-]+:[a-z0-9-]+$`, at most 64 bytes.
   `fex.ValidReporter(string) bool` checks the format only. Which values a source may
   send is the platform's decision: it accepts, per source, only the values it knows
   and refuses an upload with any other value. The field comment states the format,
   that it is not free text, and that a producer sends one reporter per upload; a
   producer with two modes sends two uploads.
3. **Documented with the contract.** `providers-sdk/v1/upstream/fex/README.md`
   describes the field, its format and how it combines with the other completeness
   fields.
4. **Additive only.** A new field; the generated Go code is regenerated, never edited.
   A request without the field encodes byte for byte as before, so existing producers
   are unaffected.

### Implementation

- `providers-sdk/v1/upstream/fex/fex.proto`: `string reporter = 14;` with its comment;
  `fex.pb.go` and `fex_vtproto.pb.go` regenerated by `go generate`.
- `providers-sdk/v1/upstream/fex/fex.go`: `MaxReporterLength = 64` and
  `ValidReporter(s string) bool`.
- `providers-sdk/v1/upstream/fex/fex_test.go`: `TestValidReporter` (accepted and
  refused formats, the 64-byte bound) and `TestReporterRoundTrip` (binary and
  proto-JSON encoding of field 14; a request without it encodes as before).
- The upload helper in cnspec gains an option that copies a reporter into the request.
  That is cnspec's change, made once an mql release carries the field.

## Security implications

- **Threat model:** a producer that sets a wrong reporter could close another mode's
  findings of the same source. The platform validates the value per source (an
  unknown reporter for a known source is refused); the SDK only carries it.
- **Authentication and authorization:** unchanged. No RPC is added; an upload is
  authenticated and authorized by the platform as today. The reporter grants nothing:
  it only narrows which of the uploader's own findings a full pull may close.
- **Data handling:** the field holds a short identifier of the producer mode, no data
  from the scanned target.
- **Supply chain:** none added; the existing protobuf toolchain (`protoc-gen-go`,
  `protoc-gen-go-vtproto` under `scripts/protoc`) generates the code.
- **Residual risk:** a producer that sends no reporter keeps today's behaviour, where a
  full pull of one mode closes the other's findings.

## Performance implications

Negligible: one string of at most 64 bytes per upload, no work per finding. No
measurement was made; none is needed for a single optional scalar field.

## Consequences

### Positive

- A producer with two modes can run full pulls of each under one source without
  closing the other's findings.
- The source stays the producing tool, so enrichment, display and existing source
  filters are unchanged.

### Negative

- Another public field to version and document.
- Producers built before the field keep the old close behaviour until they set it.
- A platform that predates the field does not act on it. A producer sets it only once
  the platform accepts it, since an ingest that refuses unknown fields would refuse
  the upload.

### Follow-up

- cnspec: an upload option that sets `reporter`, once an mql release carries field 14.
- The platform's copy of the message gains field 14 and the per-source accepted values.

## Alternatives considered

### A separate source per mode

Rejected: the source names the producing tool and drives enrichment and display.
Splitting it per mode would show one tool as two and break existing source filters.

### Infer the mode from finding properties

Rejected as the contract: it works for findings in the upload but not for an empty
full pull, which has no findings to inspect. The platform may keep it only as the
fallback for producers that predate the field.

### Another `FindingKind` value per mode

Rejected: a kind says which document type an upload carries (FEX or VEX), not which
producer mode wrote it. A mode-specific kind would mix the two and need a new enum
value for every producer.
